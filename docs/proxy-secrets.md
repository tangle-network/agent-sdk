# Proxy-held secret contract

`proxySecrets` requests credential use without delivering its value to the agent. The declaration, strict runtime schemas, scope comparison and receipt types have one owner: [agent-interface](../packages/agent-interface/src/proxy-secrets.ts). They are available from the package root and its existing `environment-provider` and `profile-schema` entry points. Read the installed schema for protocol support and accepted fields.

```ts
const profile = {
  harness: "opencode",
  proxySecrets: [{
    envName: "REPORTS_TOKEN",
    secretRef: { kind: "secret-ref", key: "reporting-api" },
    hosts: ["reports.example.com"],
    presentation: { type: "bearer" },
    methods: ["POST"],
    paths: ["/v1/events"],
  }],
};
```

The same declaration works on portable environment creation and AgentProfile. An omitted update preserves bindings; an explicit empty array requests revocation. Environment variables containing ordinary strings retain their readable meaning. A protected environment name or source reference cannot also select readable secret delivery.

## Authority and identity

A declaration is a request, never permission to reveal a secret or send it to a new destination. The trusted issuer resolves the key under authenticated tenant and issuer authority, without personal/team fallback, and pins a concrete secret identity and revision. It intersects the requested destinations, operations and lifetime with its independently authorized policy. Reviewed upstream endpoints and provider-side resource limits remain necessary: a permitted endpoint can expose credentials or issue new ones.

The requested reference, presentation, scope and lifetime participate in canonical profile identity. Candidate plans retain tagged config references and file secret-slot paths. Rotation values and generated placeholders do not belong in authored profiles, public plans, receipts or logs. Changing a reference or file slot must change identity even if the public JSON template still contains the same null bytes.

Grant expiry is bounded by issuer policy, authenticated parent expiry and absolute source validity. Computing a relative TTL when a resolver runs cannot authorize a delayed installation past the source credential expiry. The existing trusted source store and grant issuer own this cap; a profile cannot attest it. The optional grant source-expiry field records the trusted bound.

Descendants can narrow declarations and grants through the shared comparison helpers. Those comparisons do not prove authorization, active ancestry or freshness. The execution owner derives lineage from authenticated execution identity across create, restore and grant routes; omitting a parent ID cannot escape it. Different authorities require separate sandboxes because the proxy cannot identify arbitrary processes within one guest.

## Exact credential use

Hosts are exact canonical FQDNs over the transport admitted by the schema. CONNECT authority, TLS SNI and HTTP authority must agree. Network reachability and secret-use confinement are separate decisions in both open and strict egress modes. Redirects, DNS aliases and CNAMEs do not expand a credential grant.

Bearer and Basic use the complete intended credential component. Basic validates the declared public username and replaces only the password. Header selectors are case-insensitive and match one complete value. Query selectors are case-sensitive after one strict decode and affect only the named value. Duplicate selected headers or decoded query names, malformed encoding and embedded placeholders refuse use.

Path selectors are exact or terminal slash-star subtrees. The schema rejects ambiguous path spellings instead of normalizing them into a different authority decision. The machine-readable [wire cases](../packages/agent-interface/fixtures/proxy-secret-wire-v1.json) are shared inputs for client parity and the enforcement owner's wire tests; schema tests alone do not establish proxy enforcement.

Placeholders are independent, unpredictable values per sandbox epoch, generated by the trusted lifecycle owner. JWT compatibility data is synthetic and public; real upstream access, ID and refresh credentials remain outside the guest. Unsupported native authentication fails without a readable fallback.

## Installation and retained execution

A `proxy-installed` receipt acknowledges the proxy rules and is only an input to placeholder materialization. Only `installed`, with both proxy and materialization acknowledgments, permits dispatch. Receipts bind each environment name and requested reference to its concrete grant, sandbox, epoch, effective scope and expiry. A `revoked` receipt confirms removal of sandbox bindings; it does not claim upstream credential revocation. Fresh creation and readback can acknowledge an installed empty set; an explicit empty update must acknowledge revocation.

The provider negotiates declared secure requests before calling a credential resolver or allocating compute. A legacy resolver whose output introduces an undeclared secure binding can only be checked after its reference-only response; it must still refuse before allocation when custody is unsupported. No resolver response authorizes a raw-value fallback.

Creation and reconnect read the installed receipt. Retained execution revalidates custody before dispatch, including source renewal and generation-safe replacement through the existing lifecycle. A staged, expired, revoked, foreign or unacknowledged receipt cannot authorize execution. Recovery reauthorizes; clones require independent placeholders and rematerialized files. Losing an acknowledgment or contacting a partitioned host does not prove revocation complete. A generation identifies one immutable installed receipt; rotation may advance the source revision only in a newer generation while retaining the tenant, issuer and secret identity.

The core integration owner enables advertisement only after API, placement driver, proxy, host and materializer agree. Package-level tests prove this contract and adapter behavior; production confinement, rotation, snapshot custody and native-client compatibility require the program's served proofs.

## Host parent selection

`ProxySecretParents`, `ProxySecretParentsSchema` and `isProxySecretParentsTotal`
are available from the canonical package root and environment-provider entry
point. The shared wire fixture includes parent-map cases. This host control is
optional on CREATE and explicit custody attachment/PATCH; readback reports the
effective pins. It is separate from portable declarations and AgentProfile.

A supplied map has exactly one destination environment key per final binding.
A string requests an API-verified parent sandbox; null explicitly requests
independent root issuance. It contains no parent environment name or caller
grant ID. Trusted Runtime producers retain the complete map from actual
allocation state before creating, including null for fresh coordination authority.
The API projects pins from validated private parent locators without persisting
a second map. The API delegation marker is separate from engine capabilities.

An omitted map preserves existing `(envName, secretRef)` pins; new tuples in a
mapped replacement need an explicit total map. Changing a pin requires
acknowledged removal first. Policy-only PATCH cannot carry a map; empty
replacement permits an omitted or empty map and clears only after revoked
acknowledgment. Explicit maps, observed maps and delegated grants require the
API marker and exact total readback; a delegated receipt without a map refuses.
Ordinary initial root creation without a map can use the existing root protocol.

These exports establish the shared contract. Provider forwarding and the
parent-capable Sandbox SDK are qualified and released through their owners;
read their published manifests and authenticated capability document for support.
